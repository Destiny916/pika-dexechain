# 头部相机（第三视角）接入说明

> 本文记录在 Pika 采集工具上**新增一路头部视角相机**的全部改动、原理与运维方法，供后续接手者查询、部署、排错。
> 当前头部相机已做成**可配置后端**：保留原 Orbbec，也支持 KFCv2 网络相机。
> 最新决策：KFCv2 不再使用 adapter，不再发布 `/camera_head/color/image_raw`；dataCapture 直接订阅 `/camera/kfc_compressed`，采集时在线解码、拆分并保存 `pikaHeadCamera_l/r`。原始拼接 JPEG 默认不落盘，离线拆分脚本仅用于修复旧数据。完整进度见 `KFCv2头相机与HDF5改造进度.md`。

---

## 1. 一句话概述

- **加了什么**：在原有「双鱼眼 + 双 RealSense」基础上，新增**头部第三视角相机**；Orbbec 保存 `pikaHeadCamera`，KFCv2 保存左右目 `pikaHeadCamera_l/r`。
- **怎么选相机**：通过 `HEAD_CAMERA_DRIVER` 选择后端：`orbbec`（默认，原 Dabai DC1）、`kfcv2`（KFCv2 网络相机）、`none`（不启动头相机）。
- **达成什么**：录制的每个 episode 里多一个相机文件夹，图像与其他传感器**自动时间戳对齐**，开箱即用。
- **不含什么**：本次**只做「采集」**——数据能录进来、能对齐。Pika 数据 → X-VLA 训练格式（cam_high + 本体感觉）的**转换器是另一个独立项目，尚未实现**。详见第 8 节。

---

## 2. 统一接口与后端选择

Orbbec 与 KFCv2 现在保留两条不同采集链路，由 `HEAD_CAMERA_DRIVER` 选择：

| 后端 | 输入 topic | 消息类型 | 数据名 | 落盘目录 |
|----|----|----|----|----|
| `orbbec` | `/camera_head/color/image_raw` | `sensor_msgs/Image` | `pikaHeadCamera` | `episode<N>/camera/color/pikaHeadCamera/` |
| `kfcv2` | `/camera/kfc_compressed` | `sensor_msgs/CompressedImage` | `pikaHeadCamera_l/r` | `episode<N>/camera/color/pikaHeadCamera_l/` 和 `pikaHeadCamera_r/` |

头相机默认后端写在迁移包根目录 `pika_migrate.conf`，软件 setup 前先改；`migrate_software.sh` 会把它同步成项目内 `pika_runtime.env`。日常也可以用环境变量临时覆盖：

```bash
# 默认仍是原 Orbbec
bash /home/dex/app/pika/pika_ros/scripts/start_collect.sh

# 使用 KFCv2 网络头相机
HEAD_CAMERA_DRIVER=kfcv2 HEAD_CAMERA_IP=192.168.20.30 \
  bash /home/dex/app/pika/pika_ros/scripts/start_collect.sh

# 不启动头相机(排查/无头相机采集)
HEAD_CAMERA_DRIVER=none bash /home/dex/app/pika/pika_ros/scripts/start_collect.sh
```

`start_multi_sensor.bash` 中的默认值：

```bash
head_camera_driver=${HEAD_CAMERA_DRIVER:-orbbec}
head_camera_port=${HEAD_CAMERA_PORT:-52}
head_camera_ip=${HEAD_CAMERA_IP:-192.168.20.30}
```

## 3. 后端 A：Orbbec Dabai DC1（原方案）

| 项目 | 值 | 说明 |
|------|-----|------|
| 型号 | Orbbec Dabai DC1（奥比中光） | 双目结构光深度相机，本套**只用其 RGB** |
| RGB 路（用） | USB ID `2bc5:0557` | 标准 UVC（v4l2）设备，等同普通 USB 摄像头 |
| 深度路（不用） | USB ID `2bc5:0657` | 非 v4l2，需 Orbbec SDK，本套**不启用** |
| 分辨率/帧率 | 640×480，MJPG | 与鱼眼一致 |

### ⚠️ 必须插独立 USB3 控制器

头相机数据量大（640×480 MJPG ~30fps）。若和鱼眼、RealSense 挤在同一个 USB 控制器（同一个 root hub）上，会**抢带宽**，导致相机掉帧甚至打不开。
**部署时务必把头相机插到一个独立的 USB3 口**（最好是主板上物理隔开的另一组 USB），不要用同一个 HUB 串接。

## 4. 后端 B：KFCv2 网络相机

| 项目 | 值 | 说明 |
|------|-----|------|
| 运行依赖 | `dexe-sensors_0.4.3+20260630104156+a5b1db7_amd64.deb` | 安装后落到 `/opt/dexe_sensors` |
| 启动节点 | `kfcv2/kfcv2_publisher` | 从 deb 提供 |
| 相机 IP | `192.168.20.30` | 固定配置；主机相连网口需在 `192.168.20.x` 网段 |
| 输入 topic | `/camera/kfc_compressed` | `sensor_msgs/CompressedImage`，左右目横向拼接 |
| adapter | 不使用 | dataCapture 直接订阅，在独立落盘线程在线拆分左右目 |

KFCv2 日常启动由 `open_multi_sensor.launch.py` 自动完成，等价于：

```bash
source /opt/ros/humble/setup.bash
source /opt/dexe_sensors/install/setup.bash
ros2 run kfcv2 kfcv2_publisher --ros-args -p video_index:=192.168.20.30
```

然后 dataCapture 直接订阅 `/camera/kfc_compressed`，在线保存为：

```text
episode<N>/camera/color/pikaHeadCamera_l/*.jpg
episode<N>/camera/color/pikaHeadCamera_r/*.jpg
```

> SDK zip 只用于**首次搜索/修改相机 IP**，不进入日常采集链路。相机 IP 一旦确定，不会自己改变；只有未知 IP、换相机或重配网络时才需要运行 `kingfisher_cpp_cmd search-ip`。

## 5. 改动原理

Orbbec 头相机仍是「纯配置」路径：Pika 的 `sensor_msgs/Image` 相机列表由 yaml 配置驱动。KFCv2 由于要直接保存 `sensor_msgs/CompressedImage` 原包，已经对 `data_tools_dataCapture` 做了 C++ 扩展，新增 `dataInfo.camera.compressed.*` 参数，并保存到 `camera/color/<name>`。

- `dataUtility.h:230`：程序启动时用 `get_parameter("dataInfo.camera.color.names", ...)` 从 yaml 读取相机名列表。
- `dataCapture.cpp:379`：对列表里**每一个**相机的话题逐个 `subscribe`。
- `dataCapture.cpp:1743`：为每个相机名创建文件夹 `camera/color/<name>`。
- `dataCapture.cpp:1001`：收到图像后，按 `msg.header.stamp` 命名写 jpg。

**结论**：Orbbec 使用 `multi_pika_data_params.yaml`，保存到 `camera/color/pikaHeadCamera/`；KFCv2 使用 `multi_pika_kfcv2_data_params.yaml`，订阅 `/camera/kfc_compressed` 并在线保存到 `camera/color/pikaHeadCamera_l/` 和 `pikaHeadCamera_r/`。两条路径都由 `HEAD_CAMERA_DRIVER` 自动选择。

KFCv2 topic 中的图像是左右目横向拼接图。`HEAD_CAMERA_DRIVER=kfcv2` 时，压缩消息先进入队列，再由独立落盘线程在线解码、对半拆分和 resize，默认输出 `640x360` 的：

```text
episode<N>/camera/color/pikaHeadCamera_l/*.jpg
episode<N>/camera/color/pikaHeadCamera_r/*.jpg
```

输出由 `multi_pika_kfcv2_data_params.yaml` 配置：

```yaml
onlineSplit: true
saveOriginal: false
splitWidth: 640
splitHeight: 360
jpegQuality: 95
```

`split_kfc_images.py` 不再由 `run_pika.sh` 默认调用，仅用于仍保留 `pikaHeadCamera/*.jpg` 的旧 episode 或异常数据修复。

> 同理，本套的两份代码 `src/`（编译源）与 `install/`（实际运行）我都直接改了 `install/` 那份——容器挂载 `install/`，改完重启即生效，无需 `colcon build`。详见第 8 节最后一条纪律。

> **关于 `usb_camera.py` 的三处副本（重要）**：ament_python 包里这个可执行脚本实际存在三份——
> `src/sensor_tools/scripts/`（编译源）、`install/.../share/sensor_tools/scripts/`（资源拷贝）、

> launch 文件与 yaml 则在 `src/` 与 `install/share/` 两份同步（运行时读 `install/share/`）。

## 7. 数据怎么落地 & 时间戳对齐

### 落地位置

Orbbec 后端保存一路 RGB：

```text
episode<N>/camera/color/pikaHeadCamera/*.jpg
```

KFCv2 后端保存在线拆分、resize 后的左右目：

```text
episode<N>/camera/color/pikaHeadCamera_l/*.jpg
episode<N>/camera/color/pikaHeadCamera_r/*.jpg
```

每帧 jpg 以图像消息 `header.stamp` 的秒值命名，KFCv2 左右眼使用同一个输入消息时间戳，因此可按文件名一一对应。

### 为什么没有对齐风险

本套采用**软同步**：每一路传感器（鱼眼、RealSense、IMU、夹爪、定位、头相机）**各自独立**按自己的时间戳落盘，**不在采集时强行对齐**；对齐是**事后**按「最近邻时间戳」做的。

Orbbec 时间戳由 `usb_camera.py` 使用 `get_clock().now()` 生成；KFCv2 使用厂商 publisher 写入的 `header.stamp`。两种后端都沿用现有按时间戳落盘、事后最近邻对齐的机制。

### 实测验证

Orbbec 端到端验证曾成功生成 `pikaHeadCamera/`，单帧为 640×480。KFCv2 已通过完整数采流程验证：左右眼在线拆分能够跟上约 30 FPS；关闭原始图保存并重启采集后，只保存 `pikaHeadCamera_l/r`，输出为 640×360。

## 8. 新机器部署步骤

1. **选择头相机后端**：
   - Orbbec：头相机插到**独立 USB3 口**。
   - KFCv2：相机网线直连/经交换机连接主机网口；相机 IP 固定为 `192.168.20.30`，主机相连网口设为 `192.168.20.x`。
2. **装 udev 规则**（已包含在迁移脚本里，单独装则）：
   ```bash
   sudo cp pika/99-orbbec-head.rules /etc/udev/rules.d/
   sudo udevadm control --reload-rules && sudo udevadm trigger
   ```
3. **确认 Orbbec 软链生成**（使用 Orbbec 时）：
   ```bash
   ls -l /dev/video52     # 应指向头相机的 RGB capture 节点（如 video16）
   ```
   没有 `video52`？→ 见第 7 节。
4. **确认 KFCv2 deb**（使用 KFCv2 时）：
   ```bash
   test -f /opt/dexe_sensors/install/setup.bash
   ROS_DOMAIN_ID=42 bash -c 'source /opt/ros/humble/setup.bash; source /opt/dexe_sensors/install/setup.bash; ros2 pkg executables kfcv2'
   ping 192.168.20.30
   ```
5. **启动采集**：
   ```bash
   # Orbbec(默认)
   bash /home/dex/app/pika/pika_ros/scripts/start_collect.sh

   # KFCv2
   HEAD_CAMERA_DRIVER=kfcv2 HEAD_CAMERA_IP=192.168.20.30 \
     bash /home/dex/app/pika/pika_ros/scripts/start_collect.sh
   ```
6. **自检话题**（容器内）：
   ```bash
   # Orbbec
   ros2 topic info /camera_head/color/image_raw   # Publisher count 应 ≥ 1

   # KFCv2
   ros2 topic info /camera/kfc_compressed         # Publisher count 应 ≥ 1
   ros2 topic hz   /camera/kfc_compressed         # 约 30Hz
   ```

## 9. 排错 FAQ

**Q1：Orbbec 头相机没起来 / `start_collect.sh` 提示 cam_high/orbbec 没起来**
- 查 `/dev/video52` 是否存在：`ls -l /dev/video52`。不存在 → udev 没生效或相机没插好/没枚举出 RGB 路。
- 查相机是否被识别：`lsusb | grep 2bc5`，应看到 `2bc5:0557`。
- 重新触发 udev：`sudo udevadm control --reload-rules && sudo udevadm trigger`，再拔插一次相机。

**Q2：KFCv2 头相机没起来 / `start_collect.sh` 提示 cam_high/kfcv2 没起来**
- 查 deb：`test -f /opt/dexe_sensors/install/setup.bash`。
- 查容器挂载：`docker exec pika test -f /opt/dexe_sensors/install/setup.bash`。
- 查网络：主机连接相机的网口必须是 `192.168.20.x`，相机 IP 默认 `192.168.20.30`，用 `ping 192.168.20.30` 验证。
- 查 KFC compressed topic：`ros2 topic hz /camera/kfc_compressed`。

**Q3：录进去的画面不对，像是 RealSense 的画面？**
- 这是历史隐患：`usb_camera.py` 原有「偶/奇号设备节点配对回退」逻辑，若头相机的 capture 节点打不开，可能回退到隔壁号段、误开成 RealSense（USB `8086`）。
- **已修复**：头相机节点强制 `pair_fallback:=False`，**只认软链指向的那个 capture 节点**，绝不回退。如仍异常，确认 launch 里头相机节点确为 `pair_fallback=False`。

**Q4：帧率只有约 20Hz（不到设定的 30），正常吗？**
- **正常，无需处理**。`usb_camera.py` 每帧要做 MJPG 解码 + `cv2_to_imgmsg`（~900KB）+ 发 TF + 发 CameraInfo，受 Python GIL 与 `create_rate` 精度限制，实测稳定在 15~20Hz。
- 采集节点本身按 `hz=20` 工作，且软同步**不要求各路帧率一致**，故 20Hz 完全够用、不影响对齐。

## 10. 已知边界与纪律

- **X-VLA 转换未做**（本次范围外）：头相机图像对应训练格式里的 `cam_high`，对齐干净；但**整套 Pika → X-VLA 转换器**（机械臂关节 qpos/qvel/effort/action、eef 位姿等本体感觉映射）是**独立的下一个项目，尚未实现**。本次交付仅保证「数据录得进、对得齐」。
- **`pair_fallback` 的取舍**：头相机设 `False`（udev 已锁定设备，禁回退更安全）；鱼眼保持默认 `True`（鱼眼的配对节点是同一个 DECXIN 相机的两个 v4l2 节点，确实需要回退兼容），二者互不影响。
- **别随手 `colcon build`**：当前工作流是「直接改 `install/` + 容器挂载即生效」，**不需要编译**。`src/` 与 `install/share/` 的 launch 存在一处**原厂遗留**的小漂移（夹爪节点 `capture_service` 的 remap，`src` 有、`install/share` 无）。
  注意因果：launch 运行时直接读 `install/share/` 那份（缺这 2 行），所以**「运行时一直就是没有这 2 行」是当前的既成状态，与编不编译无关**；真正的风险是——一旦 `colcon build`，会把 `src` 的 2 行装进 `install/share/`，**反而改变现状**。因此这处属于「保持不动最安全」。若确需编译（改了 C++），先决定这 2 行要不要、把两份对齐再编，避免行为突变。这是夹爪原厂遗留、非本次头相机范围。
